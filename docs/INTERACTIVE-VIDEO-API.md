# วิดีโอแบบมีปฏิสัมพันธ์ เป็นบริการ — `kaiiv-service`

เครื่องยนต์ที่ตัดสินสามอย่าง และ**ไม่เก็บอะไรเลยสักอย่าง**

| ถาม | ตอบโดย |
|---|---|
| ผู้เรียนคนนี้เห็นอะไรได้บ้างบนไทม์ไลน์ | `POST /timeline` |
| คำตอบนี้ถูกไหม | `POST /judge` |
| วินาทีนี้วิดีโอเล่นต่อได้หรือยัง | `POST /due` |

คอร์ส ผู้เรียน วิดีโอ และบันทึกทั้งหมด อยู่กับ**ระบบที่เรียก** ไม่ได้อยู่ที่นี่

---

## ทำไมไม่มีฐานข้อมูล

นี่คือการตัดสินใจหลักของบริการนี้ ไม่ใช่ฟีเจอร์ที่ยังไม่ได้ทำ

วิดีโอแบบมีปฏิสัมพันธ์ถูกสร้างขึ้นเพื่อให้**มากกว่าหนึ่งระบบ**เรียกใช้ — Moodle ของเราวันนี้
และอะไรก็ตามที่เอามารวมกันวันหน้า ถ้าเครื่องยนต์เก็บข้อมูลเองด้วย สองระบบที่แชร์มันจะกลายเป็น
สองระบบที่เถียงกันว่า "ผู้เรียนคนนี้" ของใครคือตัวจริง

เครื่องยนต์ที่ไม่ถือครองอะไรเลย แชร์กันได้ทั้งคู่

ผลตามมาที่ต้องรู้: **ทุกคำขอต้องแนบข้อมูลที่ต้องใช้ไปด้วย** ไม่มี session ไม่มี cache
ยิงคำขอเดิมซ้ำได้ผลเดิม และการนับว่าตอบไปกี่ครั้งเป็นหน้าที่ของคนที่ถือบันทึก

---

## อยู่ตรงไหนในสแตก

```
docker-compose.yml
  face-service    :9000   ใบหน้า
  ai-service      :9100   ผู้ช่วยรีวิว
  kaiiv-service   :9200   ← อันนี้
  moodle          :80
```

`expose` ไม่ใช่ `ports` — **ไม่เปิดออกนอกเครื่อง** เข้าถึงได้เฉพาะในเครือข่ายของ compose

นี่ไม่ใช่การตั้งค่าเพื่อความปลอดภัยเผื่อไว้ แต่เป็นข้อกำหนด: เบราว์เซอร์ที่เข้าถึงบริการนี้ได้
คือเบราว์เซอร์ที่สั่งให้มันตรวจข้อสอบได้ และการตรวจคือสิ่งเดียวที่เบราว์เซอร์ต้องขอเองไม่ได้เลย

**ไม่มี API ที่หันออกข้างนอก และไม่มีแผนจะมี**

### กุญแจ

ส่งเป็น header `X-Proctor-Key` ค่าเดียวกับ face-service และ ai-service
— หนึ่งดีพลอย มีความลับภายในหนึ่งตัว ไม่ใช่สามตัวที่ต้องหมุนแยกกัน

`GET /health` ไม่ต้องใช้กุญแจ (healthcheck ของ container ทำงานก่อนที่ใครจะมีกุญแจ
และคำตอบไม่ได้บอกอะไรเกี่ยวกับผู้เรียนคนไหน) ที่เหลือต้องใช้ทั้งหมด

### เวอร์ชันของสัญญา

ทุกคำขอต้องมี `"contract": "1.0"` ฝั่งบริการตรวจ และปฏิเสธเวอร์ชันที่มันนิยามฟิลด์ใหม่ไปแล้ว
— ระบบที่อัปเกรดข้างเดียวจะได้คำปฏิเสธที่อ่านรู้เรื่อง แทนที่จะได้ไทม์ไลน์ที่ประกอบจากฟิลด์ที่อ่านผิด

## เอาไปใช้กับระบบอื่นยังไง

ระบบที่จะเรียกใช้ต้องมีตารางของตัวเอง 2 ตาราง (ชื่ออะไรก็ได้):

```
interaction    id, type, start, end, display, pauses, x, y, width, height,
               label, content (JSON), answers (JSON), feedback
response       interactionid, userid, response, attempt, correct, timecreated
```

**คอลัมน์ `answers` ห้ามส่งให้เบราว์เซอร์** — ส่งมาที่ `/timeline` แล้วรับสิ่งที่ส่งต่อได้กลับไป

แล้วทำสามอย่าง:

1. **ตอนครูบันทึกคำถาม** → `POST /author` → เก็บ `content` กับ `answers` คนละคอลัมน์
2. **ตอนผู้เรียนเปิดหน้า** → `POST /timeline` → ส่งผลลัพธ์ให้ player ได้ทั้งก้อน
3. **ตอนผู้เรียนตอบ** → `POST /judge` → บันทึก `store` กับ `correct` ลงตาราง response

ฝั่ง Moodle ทำไว้แล้วใน [`mod_kaiiv/classes/engine.php`](../moodle/plugins/mod_kaiiv/classes/engine.php)
อ่านไฟล์นั้นเป็นตัวอย่างการต่อ — มันสั้นโดยตั้งใจ

## สองข้อที่บริการนี้รับประกัน

### 1. เฉลยไม่ออกไปที่เบราว์เซอร์

บังคับที่ [`app/contract.py`](../kaiiv-service/app/contract.py) ด้วยสองกลไกที่พังคนละแบบ

**allowlist** — มีเฉพาะคีย์ที่ `types.py` ระบุว่าเปิดเผยได้เท่านั้นที่ถูกคัดออกไป
คีย์ใหม่ที่เพิ่มปีหน้าจะไม่ไหลออกเองเพราะมีคนลืมกรอง

**ค้นหาเฉลยในผลลัพธ์จริง** — ประกอบ payload เสร็จแล้วค้นหาคำเฉลยในนั้น
ถ้าเจอ **ไม่ส่ง** และตอบ 500 กลับไป นี่คือกลไกที่รอดจากการ refactor: คนที่เพิ่มฟิลด์
`"hint"` แล้วลืม allowlist จะถูกจับที่นี่ เพราะค้นจากตัวคำ ไม่ใช่จากชื่อคีย์

> ตอบ 500 ไม่ใช่ 422 เพราะผู้เรียกไม่ได้ทำอะไรผิด — **เรา**กำลังจะทำผิด
> และไทม์ไลน์ที่ส่งอย่างปลอดภัยไม่ได้ ต้องไม่ถูกส่งเลย: กิจกรรมพังคือการแจ้งปัญหา
> ส่วนเฉลยหลุดคือการสอบใหม่ทั้งรุ่น

**ข้อยกเว้นมีข้อเดียว และประกาศไว้ชัด** — `dragtext` ต้องส่งคำไปให้ลาก ไม่งั้นไม่มีอะไรให้ลาก
สิ่งที่ปิดคือ "คำไหนลงช่องไหน" และชุดคำถูกสลับใหม่ทุกครั้งที่ส่ง

เทสต์ที่พิสูจน์ข้อนี้อยู่ที่ [`tests/test_contract.py`](../kaiiv-service/tests/test_contract.py)
— เขียนไว้เพื่อ**เปิดให้ลูกค้าดู** มันไม่ได้ตรวจว่าฟังก์ชันไม่ใส่คีย์ชื่อ `answers`
(เทสต์แบบนั้นผ่านตลอดไปขณะที่มีคนเพิ่มคีย์ `solution` ไว้ข้างๆ)
แต่ค้น JSON ที่เบราว์เซอร์จะได้จริง หาคำที่ผู้เรียนจะมองหาจริง

### 2. ลากแถบเวลาข้ามคำถามไม่ได้

วิธีที่นึกออกก่อนคือดักตอนหัวเล่นข้ามจุดที่ตั้งไว้ — และเป็นวิธีที่ผิด เพราะลากข้ามไปเลยก็ได้
ไม่มีอะไร "ข้าม" อะไรทั้งนั้น

**คำถามถึงกำหนดเมื่อหัวเล่นอยู่ที่หรือเลยจุดนั้นแล้วและยังไม่ได้ตอบ**
เขียนแบบนี้แล้วการเล่นปกติ การลากแถบ และการกลับมาเรียนต่อพรุ่งนี้ เป็นกรณีเดียวกันหมด
ไม่เหลือกรณีที่สี่ให้ลืม

## ชนิดของปฏิสัมพันธ์

ถามได้จาก `GET /types` — อย่า hard-code ในระบบที่เรียก ระบบที่ถามจะได้ฟิลด์ใหม่ตอนเครื่องยนต์มี
ระบบที่ hard-code จะค่อยๆ เพี้ยนออกไป

| ชนิด | ตรวจ | หยุดวิดีโอ | ผู้เขียนพิมพ์ยังไง |
|---|---|---|---|
| `choice` | ✅ | ✅ | ตัวเลือก ติ๊กข้อที่ถูก 1 ข้อ |
| `multichoice` | ✅ | ✅ | ตัวเลือก ติ๊กข้อที่ถูกหลายข้อ |
| `truefalse` | ✅ | ✅ | ถูก/ผิด |
| `shorttext` | ✅ | ✅ | รายการคำที่รับได้ |
| `blanks` | ✅ | ✅ | `เมืองหลวงของ *ฝรั่งเศส* คือปารีส` |
| `dragtext` | ✅ | ✅ | เหมือน `blanks` แต่ลากคำแทนพิมพ์ |
| `marktheword` | ✅ | ✅ | `the *cat* sat on the *mat*` |
| `label` | ❌ | ❌ | ข้อความบนวิดีโอ |
| `image` | ❌ | ❌ | รูป |
| `link` | ❌ | ❌ | ลิงก์ |

**ดอกจันไม่เคยถูกเก็บลงฐานข้อมูล** `POST /author` แยกมันออกก่อน
สตริงเดียวที่เก็บไว้แล้วมี `*ฝรั่งเศส*` อยู่ข้างใน คือเฉลยที่หลุดไปแล้วและกรองทีหลังไม่ได้
เพราะตอนนั้นเฉลยกลายเป็นส่วนหนึ่งของข้อความไปแล้ว

`marktheword` ของ H5P ส่งบทความที่ครอบคำตอบด้วยดอกจันไปให้ client
ของเราส่งบทความเปล่า แล้วตรวจที่ index

### สามข้อที่จงใจไม่ให้คะแนนบางส่วน

`multichoice` `blanks` `dragtext` — ต้องถูกทุกข้อ/ทุกช่อง

ให้ครึ่งคะแนนเมื่อติ๊กถูกครึ่งหนึ่งฟังดูใจดี แต่เปิดข้อโต้แย้งเรื่องเกณฑ์ที่ทั้งผู้เรียนและผู้สอน
ตัดสินจากบันทึกไม่ได้ และทำให้คนที่ติ๊กทุกข้อยกเว้นข้อยากได้เท่ากับคนที่เข้าใจคำถามจริง

`marktheword` เหมือนกัน — ถ้านับแค่ข้อที่มาร์กถูก คนที่มาร์กทุกคำจะได้เต็ม

### ที่ให้อภัย และที่ไม่ให้

`shorttext` `blanks` `dragtext` ตัดช่องว่างซ้ำและตัวพิมพ์ใหญ่เล็กภาษาอังกฤษทิ้ง

**ไม่ตัดวรรณยุกต์หรือสระไทย** — การถือว่า ผู้ กับ ผู เป็นคำเดียวกันคือการยอมรับคำที่สะกดผิด
ไม่ใช่การผ่อนปรนเรื่องรูปแบบ ถ้าอยากรับคำที่เขียนต่างออกไป ผู้สอนเพิ่มอีกบรรทัด
— การตัดสินอยู่กับคนที่รู้เนื้อหา ไม่ใช่กับตัวปรับรูปที่แยกคำพิมพ์ผิดจากคำคนละคำไม่ออก

## เฉลยถูกปล่อยเมื่อไหร่

```
ตอบถูก                              → ปล่อยเฉลย + คำอธิบาย
ตอบผิด แต่ยังตอบใหม่ได้              → ไม่ปล่อยทั้งคู่
ตอบผิด และหมดสิทธิ์ตอบใหม่แล้ว        → ปล่อยเฉลย + คำอธิบาย
กิจกรรมไม่ให้ตอบใหม่ตั้งแต่แรก         → ปล่อยเลย
```

**ปล่อยพร้อมกันหรือไม่ปล่อยเลย** คำอธิบายที่ให้ตอนยังตอบใหม่ได้ ก็คือเฉลยในรูปประโยค
ตอบผิด → เห็นคำอธิบาย → กด "ลองใหม่" → ตอบถูกฟรี นั่นไม่ใช่การให้โอกาสตอบใหม่
แต่เป็นปุ่มแจกคะแนน

**คำนวณใหม่ทุกครั้ง ไม่ได้เก็บเป็นคอลัมน์** ธงที่เก็บไว้จะอยู่นานกว่ากฎที่สร้างมัน
และทีหลังไม่มีอะไรบอกได้ว่ามันถูกตั้งภายใต้กฎปัจจุบันหรือกฎเก่า

ราคาที่จ่ายและควรรู้ไว้: ผู้สอนที่เพิ่มจำนวนครั้งที่ตอบได้กลางคัน จะทำให้คำอธิบายที่มีคนอ่านไปแล้ว
ถูกซ่อนกลับ — ซึ่งเห็นได้และแก้กลับได้

## รหัสความผิดพลาด

ทุกคำปฏิเสธมีชื่อ ไม่ใช่แค่สถานะ

```json
{"ok": false, "error": "bad_authoring", "detail": "no option is marked correct"}
```

| `error` | สถานะ | หมายถึง |
|---|---|---|
| `unknown_type` | 422 | ชนิดที่ `types.py` ไม่รู้จัก |
| `bad_authoring` | 422 | คำถามที่สร้างไม่ได้ — ข้อความบอกว่าทำไม |
| `bad_response` | 422 | คำตอบที่อ่านเป็นคำตอบของข้อนี้ไม่ได้ |
| `bad_request` | 422 | contract ผิดเวอร์ชัน หรือ payload ผิดรูป |
| `contract_violation` | 500 | บริการกำลังจะส่งเฉลยออกไป และหยุดตัวเองไว้ |

กุญแจผิดเป็นข้อยกเว้นรูปแบบเดียว — FastAPI ตอบ `401 {"detail": "bad key"}` ตรงๆ
ส่วน `bad_key` `unreachable` และ `malformed` เป็นชื่อที่**ฝั่งผู้เรียกตั้งเอง**
(ดู `engine::read()`) เพราะ "ต่อไม่ติด" ไม่ใช่สิ่งที่บริการที่ต่อไม่ติดจะบอกได้

`bad_authoring` ถูกส่งต่อถึงผู้สอนโดยไม่แปลงรูป — ครูที่เห็น "no option is marked correct"
แก้ได้ ครูที่เห็น "error" แก้ไม่ได้
